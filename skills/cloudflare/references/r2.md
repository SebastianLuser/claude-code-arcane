# R2 object storage

S3-compatible storage with **no egress fees**: a good fit for user uploads and public assets that are downloaded a lot.

## Access paths

| From | How |
|---|---|
| A Worker | An R2 binding (`env.UPLOADS.put/get/delete`); no keys involved |
| Another backend (Node, Go…) | The S3 API at `https://<account-id>.r2.cloudflarestorage.com` with an R2 API token (access key + secret), scoped to the buckets it needs, read-only where possible |
| Browsers | **Presigned URLs** generated by the backend through the S3 API: short expiry, fixed key chosen by the server |
| Public files | A **custom domain** connected to the bucket (cacheable, behind WAF); the `r2.dev` subdomain is rate limited and meant for development only |

```ts
// S3 SDK pointed at R2
const s3 = new S3Client({
  region: "auto",
  endpoint: `https://${ACCOUNT_ID}.r2.cloudflarestorage.com`,
  credentials: { accessKeyId: R2_ACCESS_KEY_ID, secretAccessKey: R2_SECRET_ACCESS_KEY },
});
```

## Setup

```bash
npx wrangler r2 bucket create app-uploads
npx wrangler r2 bucket cors set app-uploads --file cors.json      # only if browsers upload directly
```

- CORS only for the origins and methods the frontend uses.
- **Lifecycle rules** to delete temporary uploads and abort incomplete multipart uploads.
- Public access off by default; turn it on per bucket only through a custom domain.
- Validate type and size after upload, as with any storage (`/file-uploads`).

## Things that differ from S3

Not every S3 feature or API call exists in R2 (some bucket-level features and ACLs, for example): check the R2 S3 compatibility page for the operations your SDK uses before migrating code. Storage classes are Standard and Infrequent Access; Infrequent Access has a retrieval fee and a minimum storage duration.

# Directory Structure

There are two different layouts and they are best kept apart:

- **The repo** (`claude-code-arcane/`): the source. This is where the content and the installer are edited.
- **An installed project** (`<project>/.claude/`): what `npx claude-code-arcane install <profile>` copies. Only what some profile lists gets there.

## An installed project

```
<project>/
├── .claude/
│   ├── settings.json                  # Generated: permissions, hooks and statusline
│   ├── arcane-manifest.json           # Installed profiles and the content_hashes of every file
│   ├── skills/<skill>/                # The skills of the chosen profiles, with their references/ and scripts/
│   │   └── _templates/                # templates/gamedev/, only if some profile brings gamedev rules
│   ├── agents/<division>/             # Whole divisions or single agents, depending on the profile
│   ├── rules/                         # Universal and gamedev rules together, on a single level
│   ├── hooks/                         # Every hook in hooks/ except statusline.sh (statusline.mjs is included)
│   ├── statusline.sh                  # Only with the statusline profile
│   ├── output-styles/                 # Only if some profile declares output_styles
│   ├── docs/                          # The docs that installed content names; arcane update keeps them current
│   ├── session-state/                 # Hook logs and state; ignores itself (.gitignore with *)
│   └── .arcane-trash/                 # What arcane update removes; never deleted with rm
├── .arcane/session-state/active.md    # Progress file Claude writes; ignores itself. Outside .claude/ because every edit there asks for permission
└── .claude.bak/                       # Backup of .claude/ before installing
```

Outside the project, `~/.arcane/` holds the installation registry (`installations.json`) and the content downloaded from GitHub (`cache/<version>/`). `ARCANE_HOME` redirects it.

In a git worktree, `hooks/` and `docs/` are symlinks to the main worktree; `skills/`, `agents/` and `rules/` are copied so they can diverge per branch.

## Rules: two folders in the repo, one in the project

- **`rules/`**: rules for any software stack (backend, frontend, APIs, DBs, infra, LLM apps). Generic paths like `src/api/**` or `src/components/**`.
- **`rules/gamedev/`**: gamedev-only rules (frame budgets, shaders, NPC AI, GDDs, lore). Paths like `src/gameplay/**`, `assets/shaders/**` or `design/gdd/**`.

The installer copies both into the same `.claude/rules/`, without a subfolder. That is why a name cannot repeat across the two folders: the second file would overwrite the first. The LLM-app rule is called `llm-code.md` precisely so it does not collide with `gamedev/ai-code.md`, which is the NPC AI one.

When a project is dual (for example web + game), each family applies through its own paths.

## Hooks: how they are wired

The events are defined by `src/installer.ts` when it generates `settings.json`, not by the profiles. Every installed project gets these:

| Event | Hooks |
|--------|-------|
| SessionStart | `session-start.sh` → `detect-unreal.sh` → `detect-gaps.sh` → `check-update.sh` |
| PreToolUse (`Bash\|PowerShell`) | `guard.sh` → `validate-commit.sh` |
| PreToolUse (`Write\|Edit\|MultiEdit\|NotebookEdit`) | `guard.sh` |
| PostToolUse (`Write\|Edit`) | `validate-skill-change.sh` |
| PostToolUse (all) | `session-watch.sh post-tool` (edits, loops, scope, compaction warning) |
| PreCompact / PostCompact | `pre-compact.sh` / `post-compact.sh` |
| Stop | `session-stop.sh`, `worktree-stop.sh`, `session-watch.sh stop` (format + type check of what was edited) |

Each command is `bash "$CLAUDE_PROJECT_DIR/.claude/hooks/<script>"`: inside a worktree the hooks run from the worktree, which may not have `.claude/hooks/` committed, and the variable always points to the project where the session started. `arcane update` migrates installations that had the relative path.

`guard.sh` runs `guard.mjs` with Node over the commands of Bash and of the Windows PowerShell tool (with its own forms: `Remove-Item -Recurse`, `Set-Content .env`): it denies what the user runs by hand (force push, `--no-verify`, `sudo`, writing `.env`), asks before anything destructive (`rm -rf` outside regenerable folders, deleting data, a new dependency) and when editing CI, infra, existing migrations, manifests or lint configs. Without Node it does nothing and only the static permissions remain; Arcane is installed with npx, so Node is there.

The statusline (`statusline.sh`) is configured separately, only with the `statusline` profile.
